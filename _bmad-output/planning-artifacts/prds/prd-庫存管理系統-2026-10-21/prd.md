## 1. 願景

一個**跑在自己電腦上的庫存管理系統**：把「今天進了多少、出了多少、還剩多少」這三個問題，從翻紙本、傳 Excel、靠記憶，變成一個隨手可查、每一筆都留有紀錄的系統。

它服務的是**小微企業的倉管人員與店主**（1–5 人的作業規模，無既有 ERP），以及**教學與練習場景**。對這些人而言，庫存不是天天都有大批量作業，但「數字對不上」是每個月都會發生、而且每次都要花時間回頭查的痛點。因此本產品的價值不在於複雜度，而在於：**每一次數量變動都留下可追溯的紀錄，任何時候都能回答「這個數字為什麼是這樣」**。

而當紀錄累積到一定程度，管理者自然會問出第二組問題——**接下來哪些品項要補貨、補多少？** 這需要把出庫紀錄還原成「消耗速度」，再換算成可執行的補貨建議；以及**每位銷貨員賣了什麼、賣了多少？** 這需要每一筆出貨都歸屬到人。兩者都不需要新資料來源，全部長在同一份可追溯的庫存異動之上——這正是「先把數字記對」的複利。

MVP 階段刻意不追求 ERP 級的完整度（採購、財務、供應商管理、多倉、多人權限、行動裝置原生 App 都不在 v1），而是把「商品主檔 → 入庫 → 出庫 → 庫存查詢 → 盤點 → 異動紀錄 → 補貨判斷 → 銷貨員業績 → 報表」這條主線做到**正確、可驗收、可交接**。技術選擇刻意保守：本機單機部署、PostgreSQL 現成資料庫、Web 介面，全部跑在 Windows 上，不依賴任何雲端服務或付費授權。

`[ASSUMPTION: MVP 的使用情境為單一小型倉管/店務環境、1–5 名使用者、單一營業地點、無既有 ERP 需整合。]`

## 2. 目標使用者

### 2.1 Jobs To Be Done

- **功能性**：當東西進來或發出去時，我要能在一個地方把它記下來，不用再開 Excel 改數字。
- **功能性**：當有人問「這個品項現在剩多少」時，我要能立刻給出答案，而且這個答案有紀錄可以佐證。
- **功能性**：當定期盤點發現帳面與實物不同時，我要能記錄差異、修正庫存，並保留差異原因。
- **功能性**：當我要決定下週要訂哪些貨時，我要能直接看到依近期消耗速度算出的補貨建議（哪些品項快見底、該補多少），而不是憑印象猜。
- **功能性**：當我要評估每位銷貨員的表現時，我要能看到期間內各人賣了哪些品項、多少件、多少金額，並可下鑽到明細。
- **情緒性**：我不想在月底對帳時才發現數字早就對不上，而且不確定是從哪一天開始錯的。
- **情緒性**：我希望交接給下一個人時，只要一份文件跟一個資料庫，就能讓他接手，不需要口頭交接。
- **安全性**：我需要知道誰動了數字（記錄裡要有操作者與時間）。
- **學習性**：作為正在學 AI 輔助開發的人，我需要一個真實但可控的專案，讓我練習「用 AI 把需求變成可驗收成果」的完整流程。

### 2.2 非使用者（v1）

- **一般消費者／終端客戶**：不做前台購物、會員、購物車、線上訂單。
- **供應商與採購人員**：v1 不做供應商管理、採購單、到貨預約；補貨建議只到「清單」為止。
- **財務、會計與人資**：v1 不做成本核算、總帳、稅務、應收應付，也不做薪資結算與績效考核。
- **多倉／跨店流通**：v1 只有單一庫存位置。

### 2.3 關鍵使用者旅程

> 角色皆為具名角色，情境取自課堂框架的「需求分析六問」推導，非真實訪談（見 §8 OQ-1）。

- **UJ-1. 店裡的陳姐今天早上收進三箱飲料，隔天還查得到這批貨。**
  - **角色與情境：** 陳姐是「小陳商店」的倉管兼店員，每天早上接貨、晚上盤點，靠手機記事本與紙本記帳。
  - **進入狀態：** 早上 9 點，貨送抵店門口，陳姐已登入本機系統（單機版，無權限控管）。
  - **路徑：** 陳姐開啟「入庫」→ 選品項「可樂 500ml」→ 輸入數量 36、單價 25 → 備註「2026-10-21 供應商 A 到貨」→ 送出。系統立即把庫存現量由 24 改為 60。
  - **高潮：** 陳姐在畫面上看到「入庫成功：可樂 500ml，庫存 24 → 60」，並且知道這筆會出現在月報表與補貨統計裡。
  - **收尾：** 陳姐回到櫃檯；當天下午有人問「還有多少可樂」，她打開「庫存查詢」直接看數字。
  - **邊緣情況（edge case）：** 同一箱品項被分兩次送達、數量不同 → 系統產生兩筆獨立入庫紀錄，不覆蓋。

- **UJ-2. 阿豪盤點時發現實際有 3 罐不見了。**
  - **角色與情境：** 阿豪是店主，每月底做一次盤點。
  - **進入狀態：** 月底營業結束後，店內已清點完畢，手上有實物數量。
  - **路徑：** 阿豪開啟「盤點」→ 選品項 → 輸入實盤數 57（帳面 60）→ 填寫差異原因「疑似損壞／報廢 3 罐」→ 送出盤點差異。
  - **高潮：** 系統產生一筆 `ADJUST` 庫存異動（含盤點單號與原因），庫存現量改為 57，畫面顯示「盤點差異 -3，已記錄原因」。
  - **收尾：** 阿豪在「盤點差異報表」看到本月所有差異，累積到同一品項時可判斷是否為盜損。
  - **邊緣情況（edge case）：** 連續兩次盤點同一品項，第二次又對不上 → 系統保留兩筆盤點紀錄，報表需可看出「反覆盤點仍有差異」的品項。

- **UJ-3. 小陳月底想知道「哪個品項賺得慢、該少進」。**
  - **角色與情境：** 小陳想知道本月進貨與銷售概況，決定下月的進貨量。
  - **進入狀態：** 月底，小陳坐在店裡用電腦。
  - **路徑：** 小陳開啟「報表」→ 選時間區間 2026-10-01 ～ 2026-10-31 → 查看「進銷存概況」：各品項期初、入庫、出庫、期末、換算金額。
  - **高潮：** 看到「可樂 500ml：進 120、出 96、期末 60，佔用資金 1,500 元」等資訊。
  - **收尾：** 小陳把報表匯出 CSV 存檔，作為下月訂購的依據。
  - **邊緣情況（edge case）：** 查詢區間內沒有任何異動 → 報表顯示「此區間無資料」而非空白頁或錯誤。

- **UJ-4. 新進來的實習生接手盤點，第一次操作系統。**
  - **角色與情境：** 實習生小美第一次用這套系統。
  - **進入狀態：** 店主交給她一台已安裝好的電腦，附印好的操作說明。
  - **路徑：** 小美照說明文件：開啟「盤點」→ 依序輸入各品項實盤數 → 最後統一送出「盤點單」。
  - **高潮：** 送出前系統列出「本單共 12 個品項、差異 2 個」，讓小美確認「有差異的品項必須填原因，未填不可送出」。
  - **收尾：** 盤點單送出後，系統產生對應的 `ADJUST` 異動，店主在「庫存異動紀錄」可看到這張單。
  - **邊緣情況（edge case）：** 小美填了負數或非數字 → 系統擋下並指出是哪一列，不讓她送出。

- **UJ-5. 期末盤點前，先用「低於安全庫存」清單決定要補貨的品項。**
  - **角色與情境：** 陳姐每週一盤點前想知道哪些品項快見底。
  - **進入狀態：** 週一早上開店前。
  - **路徑：** 陳姐開啟「庫存查詢」→ 勾選「只看低於安全庫存」→ 系統列出 3 個品項與各自的安全庫存門檻。
  - **高潮：** 清單直接可列印或複製成訂貨清單（供應商管理不在 v1，但清單是本系統的產出）。
  - **收尾：** 陳姐把清單交給跑商的供應商，本週進貨後回系統入庫，該品項離開警示清單。

- **UJ-6. 老闆陳姐用「補貨建議」決定這週要訂哪幾箱貨。**
  - **角色與情境：** 陳姐是店主，每週一固定做下週的訂貨決策。
  - **進入狀態：** 週一早上，手上有上一週的銷售狀況，想知道「哪些品項在補貨前置天數內會用完、該補多少」。
  - **路徑：** 陳姐開啟「補貨判斷」→ 選擇計算區間（最近 30 天）與補貨前置天數（7 天）→ 系統列出建議清單：品項、庫存現量、日均消耗、預計用完日、建議進貨量。
  - **高潮：** 清單上「優酪乳 500ml：現有 12、日均消耗 4.3、7 天內用完、建議補 30」——她直接照單下單。
  - **收尾：** 貨到後入庫，該品項離開建議清單；若這週銷售不如預期，下週的建議量會自動變小。
  - **邊緣情況（edge case）：** 某品項最近 30 天完全沒有出庫紀錄 → 不列入建議清單，改列於「無消耗資料（可能滯銷）」清單，避免把滯銷品一直補進來。

- **UJ-7. 老闆看這個月每位銷貨員的業績。**
  - **角色與情境：** 店主想了解三位店員各自的銷售表現，決定下月的排班。
  - **進入狀態：** 每月初，店主在店裡用電腦。
  - **路徑：** 店員小美今天出貨時在出庫單選了自己（小美）→ 店主開啟「銷貨員業績」→ 選期間「本月」→ 看到三人排名：銷售金額、件數、品項數。
  - **高潮：** 點擊「小美」下鑽，看到她本月賣出的每一筆明細（品項、數量、金額、日期、單號），加總等於彙總數字。
  - **收尾：** 店主匯出本月業績 CSV 作為內部參考（不作為薪資計算依據，見 §5）。
  - **邊緣情況（edge case）：** 某筆出庫未指定銷貨員 → 不計入任何人業績，但在「未歸屬銷售」合計中列出，讓店主知道有資料漏掉。

## 3. 詞彙表

> 全文（FR / UJ / SM）一律使用下列名詞，不得使用同義詞。

- **品項（Product）** — 可被管理的商品主檔，具唯一 `sku`、名稱、分類、單位、單價、安全庫存、啟用狀態。俗稱「商品」「貨品」，但本文件一律稱「品項」。
- **庫存現量（Stock Balance）** — 某品項**目前**持有的數量。為庫存異動的累加結果，不可直接編輯，只能由入庫／出庫／盤點差異改變。
- **安全庫存（Safety Stock）** — 品項設定的補貨門檻數量；庫存現量低於此值即進入警示清單。
- **庫存異動（Stock Movement）** — 一筆不可分割的數量變動紀錄，含品項、類型、數量、時間、單據號、備註、記錄者。分為入庫、出庫、盤點差異三種類型。
- **入庫（Stock-in）** — 庫存異動類型之一，數量增加，用於收貨、退貨入庫、盤點盈餘。
- **出庫（Stock-out）** — 庫存異動類型之一，數量減少，用於銷售、內部領用、報廢。
- **盤點（Stocktake）** — 一次性的庫存清點作業，由一張**盤點單**涵蓋多個品項。
- **盤點單（Stocktake Sheet）** — 盤點作業的單據，記錄本次盤點的品項、帳面數、實盤數、差異與原因。
- **盤點差異（Adjustment）** — 盤點單上帳面數與實盤數的差額；確認後以 `ADJUST` 類型的庫存異動寫入，並強制附上差異原因。
- **單據（Document）** — 具唯一單號的作業憑證。v1 有三種：入庫單、出庫單、盤點單。同一張單據可包含多個品項。
- **入庫單（Stock-in Sheet）** — 一次收貨作業的單據，含供貨來源備註，可含多個品項。
- **出庫單（Stock-out Sheet）** — 一次銷售或領用作業的單據，可含多個品項，並可歸屬一位**銷貨員**。
- **分類（Category）** — 品項的粗分群組（自由文字，例：飲料、零食、耗材），用於查詢與報表彙總。
- **單位（Unit）** — 品項的計量單位（例：個、瓶、箱、公斤）。
- **警示清單（Low-stock List）** — 列出所有庫存現量低於安全庫存的品項，供補貨判斷。
- **補貨判斷（Replenishment Review）** — 依出庫歷史估算各品項消耗速度，判斷哪些品項需要補貨、應補多少的功能群（FR-19 ～ FR-21）。
- **消耗速度（Consumption Velocity）** — 某品項在指定計算區間內的出庫數量，折算為「日均消耗」。預設區間為最近 30 天。
- **計算區間（Calculation Window）** — 計算消耗速度與補貨建議所採用的時間範圍（v1 提供 7／30／90 天三選一）。
- **補貨前置天數（Lead Time）** — 從下單到貨品實際進貨的預估天數。v1 為可設定參數（預設 7 天），用於估算補貨量。
- **補貨建議（Replenishment Suggestion）** — 系統依庫存現量、安全庫存、日均消耗與補貨前置天數計算出的建議進貨品項與建議數量。
- **無消耗資料（No-movement Items）** — 計算區間內完全沒有出庫紀錄的品項清單，供判斷滯銷，不列入補貨建議。
- **銷貨員（Salesperson）** — 登入帳號的一種角色（`users.role = salesperson`）。出庫單的歸屬取自登入身分，不需要另外挑選；供業績統計使用。
- **使用者（User）** — 具帳號、密碼與角色的登錄身分。四種角色：管理員、倉管、銷貨員、唯讀。
- **業績（Sales Performance）** — 某位銷貨員在指定期間內的銷售彙總：銷售金額、件數、品項數，以及其下鑽明細。
- **未歸屬銷售（Unattributed Sales）** — 指定期間內未指定銷貨員的出庫合計。v0.5 起出庫歸屬取自登入身分，正常情況下不會出現；管理員可手動指定他人歸屬時才可能出現。
- **記錄者（Recorded By）** — 造成該筆庫存異動的使用者標示。v0.5 起**一律取自登入帳號（自動帶入）**，不接受前端傳入；管理員代填單據時記錄管理員本人。
- **進銷存概況（Stock Summary）** — 報表之一：指定時間區間內各品項的期初、入庫、出庫、盤點差異、期末與金額彙總。
- **期初／期末（Opening／Closing Balance）** — 報表區間起點／終點的庫存現量。

## 4. 功能

> FR 編號為全域編號。`[ASSUMPTION]` 表示該敘述由我推論、未經確認；完整索引見 §9。

### 4.1 品項主檔管理

**說明：** 使用者建立與維護品項主檔（品項的 sku、名稱、分類、單位、單價、安全庫存）。品項是所有其他功能的依附對象；被庫存異動引用過的品項不可刪除，只能停用（`is_active`）。本功能支援 UJ-1（入庫時要先有品項）、UJ-5（安全庫存來源）、UJ-6（補貨建議的計算對象）。

**功能需求：**

#### FR-1：建立品項

使用者可在未建立任何單據的情況下新增品項，輸入 sku、名稱、分類、單位、單價、安全庫存。

**後果（可測試）：**
- 輸入完整且 sku 未重複時，系統建立品項並回傳「品項已建立」。
- sku 重複時，系統拒絕儲存並指出是與哪一個既有品項重複。
- 名稱或 sku 留空時，系統拒絕儲存並標示缺漏欄位。
- 單價可為 0 或留白（預設 0），但 sku 與名稱必填。

#### FR-2：查詢與篩選品項

使用者可依關鍵字（sku 或名稱部分相符）、分類、啟用狀態查詢品項清單，並可排序。

**後果（可測試）：**
- 關鍵字查詢結果為部分相符時，全部符合的品項都應出現，且結果依建立順序穩定排序。
- 分類無資料時顯示「查無結果」，不顯示空白表格。
- 單一頁面查詢結果上限 100 筆，超過時提供分頁。

#### FR-3：修改與停用品項

使用者可修改品項的欄位、將品項設為停用（不可再被新單據選用），並可查詢停用品項。

**後果（可測試）：**
- 停用後，該品項不出現在新建單據的品項選擇清單中，但歷史庫存異動仍可查詢且保留原名稱。
- 已被引用的品項不可刪除，系統顯示「此品項已有庫存異動紀錄，請改用停用」。

**Out of Scope（不屬於此 FR）：** 批次匯入／匯出品項（列為 v2 候選，見 §5 與 §8 OQ-6）。

---

### 4.2 入庫作業

**說明：** 使用者建立入庫單，記錄一次收貨（可多品項），送出後批次產生入庫類庫存異動並更新庫存現量。對應 UJ-1。單據在送出後不可編輯，錯誤以「反向出庫／盤點差異」更正（見 §4.4 的更正機制）。入庫資料同時是**補貨統計**的輸入（FR-20）。

**功能需求：**

#### FR-4：建立並送出入庫單

使用者可建立入庫單，輸入單號（可自動產生）、收貨日期、供貨來源備註，以及多個品項與其數量、單價。

**後果（可測試）：**
- 送出後，庫存現量等於「原值 + 該單所有品項數量總和」，多品項單據一次完成更新。
- 數量為 0 或負數時拒絕送出，並指出是哪一列。
- 同一品項在同一張單出現兩列時，系統合併為一筆或要求合併後才可送出（需使用者確認行為）。
- 送出成功後畫面顯示「入庫成功」並列出「品項：原數 → 新數」的對照。

#### FR-5：查詢入庫歷史

使用者可依時間區間、品項、單號查詢入庫單與入庫異動。

**後果（可測試）：**
- 指定品項與區間後，結果只含該品項在區間內的入庫紀錄，且可由結果反查到原單據。
- 區間內無資料時顯示「此區間無資料」。

#### FR-6：入庫單的更正

已送出的入庫單不可直接修改；使用者可對單據整體或單一品項做「沖銷（反向入庫）」以更正錯誤。

**後果（可測試）：**
- 沖銷會產生一筆方向相反的庫存異動，兩筆異動互相連結可追溯，且原始單據與沖銷單都保留。
- 沖銷後的庫存現量 = 沖銷前數量 − 原入庫數量。

**Out of Scope：** v1 不做「刪除已送出單據」；所有更正一律以反向紀錄表達（稽核要求，見 §4.6）。

---

### 4.3 出庫作業

**說明：** 使用者建立出庫單，記錄銷售或內部領用，數量不得使庫存現量為負（除非使用者具備「允許負庫存」權限，v1 預設為否）。出庫單可歸屬一位**銷貨員**，是**業績統計**的唯一資料來源（FR-23、FR-24）。對應 UJ-3 的銷售情境、UJ-7 的業績情境。

**功能需求：**

#### FR-7：建立並送出具庫單

使用者可建立出庫單，輸入單號、日期、用途（銷售／領用／報廢）、多個品項與數量；用途為「銷售」時須指定一位**銷貨員**。

**後果（可測試）：**
- 送出後，庫存現量等於「原值 − 出庫數量」。
- 當出庫數量超過庫存現量時，系統拒絕送出並顯示「庫存不足：品項 X 現有 N，需 M」。
- 用途為「報廢」時，異動備註可記錄原因，且與盤點差異在報表中可區分。
- 用途為「銷售」但未指定銷貨員時，系統拒絕送出並提示「請選擇銷貨員」。
- 用途為「領用」或「報廢」時可不指定銷貨員；此類出庫不計入任何人的業績（見 FR-24）。

#### FR-8：查詢出庫歷史

依時間區間、品項、用途查詢出庫紀錄。

**後果（可測試）：**
- 結果可依品項、日期、數量排序。
- 查詢結果的數字與「進銷存概況」報表中同一區間的出庫合計一致（一致性驗收點）。
- 查詢結果可依銷貨員篩選。

---

### 4.4 庫存查詢與警示

**說明：** 顯示目前庫存現量、依品項／分類／關鍵字查詢，並提供低於安全庫存的警示清單。對應 UJ-5。警示清單是補貨判斷（FR-19）的基礎視圖。

**功能需求：**

#### FR-9：查詢庫存現量

使用者可查看每個品項的庫存現量、更新時間，並以關鍵字或分類篩選。

**後果（可測試）：**
- 顯示值與資料庫中的 `stock.qty` 完全一致（以 SQL 查詢比對驗收）。
- 從未有任何異動的品項顯示為 0，而非空白。
- 查詢回應時間在 1,000 筆品項、1 萬筆異動的資料量下不超過 2 秒。

#### FR-10：低於安全庫存的警示清單

系統列出所有庫存現量低於安全庫存的品項，顯示品項、目前數量、安全庫存與差距。

**後果（可測試）：**
- 清單只含「庫存現量 < 安全庫存」且品項為啟用狀態者。
- 品項入庫後數量補足，清單在下一次查詢時不再顯示該品項。
- 安全庫存為 0 的品項不出現在警示清單。

---

### 4.5 盤點作業

**說明：** 使用者建立盤點單，輸入各品項實盤數，系統比對帳面數產生差異，強制填寫差異原因後送出，送出時批次產生盤點差異類庫存異動。對應 UJ-2、UJ-4。盤點差異會影響期末餘額，進而影響補貨建議的準確度（見 FR-19）。

**功能需求：**

#### FR-11：建立盤點單並輸入實盤數

使用者可建立盤點單、輸入盤點日期、逐品項輸入實盤數（可只盤點部分品項），系統即時顯示帳面數與暫定差異。

**後果（可測試）：**
- 輸入實盤數後即時顯示差異值（正 = 盤盈、負 = 盤虧）。
- 帳面數取自送出當下的庫存現量，並在畫面上標明「盤點基準時間」。
- 實盤數為負數或非數字時擋下該欄位輸入。

#### FR-12：送出盤點單與強制填寫差異原因

送出前，系統列出本單差異清單；有差異的品項必須填寫原因才能送出。

**後果（可測試）：**
- 有任一差異品項未填原因時，無法送出，並指出缺哪一列。
- 送出後產生對應的盤點差異類庫存異動，庫存現量更新為實盤數。
- 送出後盤點單不可修改；更正方式為另開新單（見 FR-13 的反向調整）。

#### FR-13：盤點差異報表

使用者可依品項或時間區間查詢歷次盤點差異，辨識反覆出現差異的品項。

**後果（可測試）：**
- 報表顯示品項、盤點時間、帳面數、實盤數、差異量、原因、盤點單號。
- 同一品項在報表中的所有紀錄可依時間排序，便於看出「反覆盤點仍有差異」。

**Out of Scope：** v1 不做盤點差異的責任歸屬分析、不做盤點任務指派與審核流程。

### 4.6 庫存異動紀錄與稽核

**說明：** 所有數量變動都會留下庫存異動紀錄。這個功能是整個產品的信任基礎（可回答「這個數字為什麼是這樣」），也是 §1 願景的核心承諾，同時是**補貨統計**（消耗速度）與**業績統計**的共同資料底層。

**功能需求：**

#### FR-14：查詢庫存異動明細

使用者可依品項、類型（入庫／出庫／盤點差異）、時間區間查詢庫存異動紀錄。

**後果（可測試）：**
- 任一品項的異動紀錄，依序套用後的累加結果必須等於目前的庫存現量（可重算驗收）。
- 每筆異動顯示：時間、品項、類型、數量、當時庫存現量、單據號、備註、記錄者。

#### FR-15：異動紀錄不可竄改

已產生的庫存異動不得被修改或刪除；任何更正都以新增反向紀錄的方式進行。

**後果（可測試）：**
- 嘗試以任何介面修改或刪除既有異動時，系統拒絕並保留原紀錄。
- 所有更正紀錄都與被更正的原始紀錄互相連結，可從任一端追溯到另一端。

#### FR-16：匯出異動紀錄

使用者可將查詢結果的異動紀錄匯出為 CSV。

**後果（可測試）：**
- 匯出檔案的列數與畫面結果列數一致，欄位順序固定。
- 以 Excel 開啟中文欄位與內容不亂碼（UTF-8 with BOM）。

### 4.7 報表

**說明：** 提供進銷存概況與庫存總值，支援區間查詢與匯出。對應 UJ-3、UJ-5。

**功能需求：**

#### FR-17：進銷存概況報表

使用者可依時間區間產生各品項的期初、入庫、出庫、盤點差異、期末與金額彙總報表。

**後果（可測試）：**
- 期末 = 期初 + 入庫 − 出庫 + 盤點差異（可重算驗收）。
- 金額以「數量 × 單價」計算並四捨五入至小數第二位。
- 報表可依品項、分類彙總，並可匯出 CSV。

#### FR-18：庫存總值一覽

顯示目前所有品項的庫存現量與占用金額，以及高／低庫存排行。

**後果（可測試）：**
- 總值為各品項「庫存現量 × 單價」加總，與逐品項加總一致。
- 排行可依金額或數量排序。

### 4.8 補貨判斷（統計是否要補貨）

**說明：** 這是使用者明確要求的功能（2026-10-21）。系統依**歷史出庫紀錄**估算各品項的消耗速度，結合庫存現量、安全庫存與補貨前置天數，判斷「哪些品項要補貨、該補多少」，並輸出可直接交給跑商的清單。對應 UJ-6。

設計原則：**公式可解釋、结果可手算、課堂可驗收**——不使用機器學習模型，所有欄位都能在課堂上重算一遍（見 A-16）。

**功能需求：**

#### FR-19：補貨建議清單

使用者可開啟補貨判斷畫面，選擇**計算區間**（7／30／90 天），系統列出建議補貨的品項。**補貨前置天數為品項層級欄位**（每個品項可有不同交期，預設 7 天），於品項主檔維護（OQ-11 已於 2026-10-21 決定）。

**後果（可測試）：**
- 每列顯示：品項、庫存現量、安全庫量、日均消耗、預計用完日、建議進貨量。
- 日均消耗 = 計算區間內該品項的出庫總量 ÷ 區間天數（區間內無出庫者不計入建議清單，改列 FR-19 的無消耗資料清單）。
- 建議進貨量 = max(0, 安全庫存 + 日均消耗 × **該品項自己的**補貨前置天數 − 庫存現量)，取整數且不小於 0。
- 只有「庫存現量 < 安全庫存 + 日均消耗 × 補貨前置天數」的品項才會出現在建議清單（即在補貨前置天數內會用完者）。
- 切換計算區間後，建議清單內容隨之改變（同一筆資料、不同區間可得出不同結果）。
- 計算區間內沒有任何出庫紀錄的品項，列入「無消耗資料」清單，不列入建議清單。
- 畫面上必須標示計算區間、每個品項所用的補貨前置天數與計算時間，避免使用者誤認數字。

#### FR-20：補貨統計報表

使用者可依時間區間查詢各品項的補貨相關統計：區間內入庫量、出庫量、期初期末、平均庫存、消耗速度、補貨次數。

**後果（可測試）：**
- 期末 = 期初 + 入庫 − 出庫 + 盤點差異（與 FR-17 同一組驗收條件）。
- 補貨次數 = 區間內該品項的入庫單張數（同一張單多列不重複計數）。
- 平均庫存以「(期初 + 期末) ÷ 2」近似計算，畫面需標示為近似值。
- 報表可依分類彙總並匯出 CSV。

#### FR-21：匯出補貨建議清單

使用者可將補貨建議清單匯出為 CSV 或列印，供交給跑商或供應商。

**後果（可測試）：**
- 匯出內容包含品項、庫存現量、日均消耗、建議進貨量，欄位與畫面一致。
- CSV 以 UTF-8 with BOM 儲存，Excel 開啟中文不亂碼。
- 匯出檔案內需標註計算區間與補貨前置天數（否則收件者無從判斷依據）。

### 4.9 銷貨員業績

**說明：** 這是使用者明確要求的功能（2026-10-21）。每一筆「銷售」用途的出庫單可歸屬一位銷貨員，系統據此彙總各人的銷售金額、件數與品項數，並可下鑽到明細。對應 UJ-7。

**功能需求：**

#### FR-22：銷貨員檔案管理

使用者可新增、修改、停用銷貨員（姓名或代號）。

**後果（可測試）：**
- 新增後，該銷貨員立即出現在出庫單的銷貨員下拉清單中。
- 已被出庫單引用的銷貨員不可刪除，只能停用；停用後不可再被新出庫單選用，但歷史業績仍可查詢（業績顯示當時名稱）。
- 姓名或代號重複時拒絕儲存並指出重複對象。

#### FR-23：出庫單歸屬銷貨員

出庫單可指定一位銷貨員；用途為「銷售」時為必填欄位。

**後果（可測試）：**
- 指定銷貨員的出庫單送出後，該筆金額與件數出現在該銷貨員的業績中。
- 未指定銷貨員的出庫單（領用／報廢）不計入任何人的業績，並出現在「未歸屬銷售」合計中。
- 出庫單送出後不可直接修改歸屬；如需更正，以「沖銷原單 + 重開單據」處理（沿用 FR-6 的更正原則），確保稽核完整。

#### FR-24：銷貨員業績統計

使用者可依期間（本週／本月／上月／自訂區間）查看各銷貨員的業績彙總與排名。

**後果（可測試）：**
- 每位銷貨員顯示：銷售金額、件數（數量加總）、品項數（distinct 品項）。
- 銷售金額 = 期間內用途為「銷售」的出庫數量 × 該品項單價。
- 排名依銷售金額由高至低；可切換以件數排名。
- 期間內無銷售紀錄的銷貨員仍列出（顯示 0），不從清單中消失。
- 畫面另顯示「未歸屬銷售」合計（金額與件數），提示歸屬遺漏。

#### FR-25：業績明細與下鑽

使用者可點選某位銷貨員查看其期間內的每一筆銷售明細。

**後果（可測試）：**
- 明細列顯示：日期、單號、品項、數量、單價、金額。
- 該明細加總必須等於 FR-24 的彙總數字（可重算驗收）。
- 每筆明細可連結回原出庫單。

#### FR-26：匯出業績報表

使用者可依條件（期間、品項、銷貨員）匯出業績彙總與明細為 CSV。

**後果（可測試）：**
- 匯出檔案同時包含「彙總」與「明細」兩種粒度，或由使用者選擇其一。
- 匯出內容與畫面顯示一致，且以 Excel 開啟中文不亂碼。

### 4.10 使用者帳號、登入與角色權限

**說明：** v0.5 新增（使用者指定）。使用者必須以帳號密碼登入才能使用系統；登入身分決定「**記錄者**」與**銷貨員**歸屬，並依角色限制可做的操作。**帳號由管理員建立，不開放自助註冊**；第一次使用時以命令列指令建立第一個管理員。

**角色與權限**

| 角色 | 可做 | 不可做 |
|------|------|--------|
| **管理員**（admin） | 全部功能，含帳號管理 | — |
| **倉管**（clerk） | 入庫、出庫、盤點、品項維護、查詢、報表、匯出、業績查看 | 建立／停用帳號、改他人密碼 |
| **銷貨員**（salesperson） | 開出庫單（自動歸屬自己）、查庫存、看自己業績 | 入庫、盤點、品項維護、帳號管理 |
| **唯讀**（viewer） | 查詢、看報表、看補貨建議與業績 | **任何寫入操作**（入庫、出庫、盤點、品項異動、帳號管理） |

**功能需求：**

#### FR-27：建立第一個管理員

第一次部署時，使用者以命令列指令（`flask create-admin`）建立第一個管理員帳號；密碼於當場輸入，不落地任何檔案。

**後果（可測試）：**
- 指令會提示輸入帳號、姓名、密碼與密碼確認；兩次密碼不一致則拒絕建立。
- 密碼至少 8 碼；不符合時拒絕建立並說明要求。
- 建立成功後輸出「管理員已建立：<username>」，且該帳號可在網頁端登入。
- 已存在管理員時，指令拒絕執行並提示「已有管理員，請用網頁端新增帳號」。
- 過程中不把密碼寫入檔案、不印到 log。

#### FR-28：登入、登出與取得目前使用者

使用者以帳號與密碼登入；登入狀態以 session 保存。

**後果（可測試）：**
- 帳號密碼正確 → 登入成功，回傳使用者資訊（帳號、姓名、角色），前端導向品項頁。
- 密碼錯誤或帳號不存在 → 回 401，錯誤訊息為「帳號或密碼錯誤」（不透露是哪一項錯誤）。
- 已停用的帳號 → 拒絕登入，訊息為「此帳號已停用，請聯絡管理員」。
- 登入後可呼叫「取得目前使用者」端點取得身分；未登入時回 401。
- 登出後所有需要登入的端點都回 401。

#### FR-29：管理員建立與管理帳號

管理員可在介面上建立帳號、停用帳號、調整角色，以及重設他人密碼。

**後果（可測試）：**
- 建立帳號時帳號不可重複；密碼至少 8 碼。
- 角色只能選四種之一。
- 停用帳號後，該帳號無法再登入；其歷史紀錄（異動、單據、業績）仍可查詢。
- 管理員不能停用或降級「自己」，避免把系統鎖死（此情況需明確提示）。
- 非管理員呼叫這些端點 → 回 403，且不透露帳號是否存在。

#### FR-30：依角色限制操作

系統依登入者的角色限制可執行的操作。

**後果（可測試）：**
- 唯讀帳號呼叫任何寫入端點 → 回 403，錯誤訊息說明「唯讀帳號不能進行此操作」。
- 銷貨員呼叫入庫或盤點端點 → 回 403。
- 倉管呼叫帳號管理端點 → 回 403。
- 未登入呼叫任何受保護端點 → 回 401。

#### FR-31：記錄者與歸屬自動帶入登入身分

所有單據的「記錄者」與出庫的銷貨員歸屬，一律取自登入身分，不接受前端傳入。

**後果（可測試）：**
- 建立入庫單時，記錄者自動等於登入帳號；即使前端夾帶其他值也不影響結果。
- 銷貨員建立出庫單時，歸屬自動為自己；管理員可指定他人（需在後端檢查權限）。
- 業績統計以登入帳號為母體，**不再有「未歸屬銷售」**，UX-DR11 的相關警示可移除。

### 4.11 跨領域非功能需求（NFR）

> 本節的需求適用於全部功能，不屬於單一功能。技術實作選擇屬於架構文件範疇（`bmad-architecture`），此處只寫「必須達成什麼」。

**NFR-1 部署與環境**
- 系統可在本機 Windows 環境以單一啟動指令啟動，不依賴雲端服務、付費授權或外部 SaaS。
- **既定技術棧（使用者 2026-10-21 指定）**
  - 前端：**React**（建置工具 Vite），以 **JavaScript（JSX）** 實作而非 TypeScript，介面語言繁體中文。
  - 後端：**Python + Flask**，資料存取使用 **SQLAlchemy**。
  - 資料庫：**PostgreSQL 18**，沿用現有實例與 `ailearn` 資料庫；schema 以 **Flask-Migrate（Alembic）** 遷移腳本管理。
  - 開發與輔助工具：OpenCode（BMAD 流程）＋ CMD 終端機。
- `[ASSUMPTION: Python 執行環境沿用本機現有 Python 3.14.7，專案另建虛擬環境；`psycopg` 對 Python 3.14 的 wheel 可用性待驗證（A-24）。]`
- `[ASSUMPTION: 正式啟動時由 Flask 同時提供 API 與前端靜態檔，以達成「單一啟動指令」；開發期則前後端各自啟啟（Vite dev server + proxy）。見 OQ-16、A-23。]`
- 課堂簡報已建立的環境前提（CMD 為預設 shell、Node.js 已安裝、OpenCode 為主要開發工具）視為既定，不需重複安裝；Node.js 僅供 OpenCode 與前端建置工具使用，後端語言為 Python。
- **開發期啟動方式（已定案，OQ-16）**：兩個終端機 — 終端機 A 跑 Flask（`http://127.0.0.1:5000`，提供 `/api/*`），終端機 B 跑 Vite dev server（`http://127.0.0.1:5173`，`/api` 轉發到 Flask）。**正式啟動／上課展示時**：`npm run build` 產出前端靜態檔，Flask 同時提供 API 與靜態檔，只要一個指令、一個網址。
- **Python 依賴管理（已定案，OQ-17）**：使用 `uv`（環境已有 uv 0.13.1）。`uv venv` 建虛擬環境、`uv add <pkg>` 安裝、`uv lock` 鎖版本，lock 檔納入版控；與 BMAD 的 Python 腳本共用同一套工具鏈。

**NFR-2 資料庫與資料**
- 系統沿用現有 PostgreSQL 18.6 實例與 `ailearn` 資料庫；schema 以 **Flask-Migrate（Alembic）遷移腳本**管理，可由空庫一鍵升級至最新版，**禁止以手改資料庫的方式變更結構**。
- 遷移腳本與應用程式的資料庫連線字串一律由環境變數注入；`alembic.ini`、設定檔與原始碼中不得出現明文密碼（見 A-25）。
- 資料庫密碼一律由使用者於執行時輸入或由環境變數提供，**不得**寫入任何檔案、原始碼、範本或版本控制。
- 不得建立明文密碼檔（`pgpass.conf`）、不得修改 `pg_hba.conf`、不得重啟資料庫服務（既有 `協作區\AGENTS.md` 硬性規則）。
- 所有時間戳以資料庫時區或明確宣告的固定時區儲存；報表以同一時區呈現。
- 補貨建議與業績統計的所有計算必須可由原始異動重算，不使用預先計算的快取數字（保證教學可驗收）。

**NFR-3 效能**
- 一般操作（開啟頁面、查詢清單、送出單據）在一般辦公電腦上回應時間 ≤ 2 秒。
- 查詢 1,000 筆品項、10,000 筆庫存異動的資料量下，FR-9 的查詢 ≤ 2 秒。
- 批次更新（單張單據多品項）在 100 品項以內應為單一交易，失敗時整批 rollback。
- 補貨判斷與業績統計在上述資料量下，各 ≤ 3 秒完成。

**NFR-4 可靠性與資料完整性**
- 送出單據與更新庫存現量必須在同一資料庫交易內完成，不允許部分成功。
- 庫存現量不得因一般操作變成負數（FR-7）。
- 應用層不得繞過庫存異動直接修改 `stock.qty`（除非透過盤點差異流程）。

**NFR-5 易用性與可交接性**
- 介面語言為繁體中文；主要操作不需閱讀說明文件即可完成（第一天上線者可獨立完成入庫與盤點）。
- 提供一份可交付的操作手冊（Markdown 與 HTML 雙格式，與現有 `使用手冊.md`／`.html` 風格一致），需涵蓋補貨判斷與業績功能的使用說明與**公式說明**（讓讀者能自己手算驗證）。

**NFR-6 稽核與可追溯**
- 每筆庫存異動都記錄時間、品項、類型、數量、單據號與記錄者。
- 任何數字都可從「目前庫存現量」反向追溯到每一筆造成它的異動；補貨建議與業績數字同樣可下鑽到原始單據。

**NFR-7 資料匯出**
- 所有查詢結果清單（品項、入庫、出庫、異動、報表、警示清單、補貨建議、補貨統計、業績）皆可匯出 CSV，內容為 UTF-8 with BOM，可直接以 Excel 開啟。

**NFR-8 測試與可驗收**
- 核心規則（入庫、出庫、盤點差異、報表期末計算、負庫存阻擋、密碼不落地）具備自動化測試或可重複執行的驗收腳本。
- 補貨建議公式與業績彙總必須有「手算對照」測試案例（給定固定資料 → 預期建議量與預期業績額）。
- 驗收條件格式遵循課程框架的「可測試、可量化、可驗收」要求（見附錄 C）。

**NFR-9 開發流程（AI 輔助）**
- 開發過程需留下可追溯的決策紀錄（PRD、架構、epic/story、驗收結果），供課堂成果發表。
- 密碼、連線字串等敏感資訊不得進入 AI 對話紀錄、產出文件或版本控制。

**NFR-10 認證與 Session 安全**
- 使用者密碼**只能以單向雜湊儲存**（不可逆、含隨機 salt），資料庫中不得出現明文密碼。
- 密碼不得寫入任何檔案、log、錯誤訊息或 API 回應；`/api/auth/login` 的錯誤訊息不得透露「帳號不存在」與「密碼錯誤」的差別。
- 登入狀態以 **HttpOnly + SameSite=Lax 的 session cookie** 保存；cookie 內容為簽章後的 session id，不可被 JavaScript 讀取。
- 未登入者不得存取任何受保護端點（回 401）；角色不符回 403。
- 登入與變更密碼的操作需記錄時間與來源（登入成功／失敗）。
- 密碼政策：至少 8 碼；v1 不強制複雜度與定期更換（教學情境權衡），但需在介面上說明建議。

## 5. 非目標（明確不做）

- **不做**供應商／採購管理、詢價、到貨預約、訂單建議（v2 候選，見 §8 OQ-5）。補貨判斷只輸出「建議清單」，不代為下單。
- **不做**會計與成本核算：成本分攤、總帳、稅務、應收應付一律不做。
- **不做**薪資結算、獎金計算、績效考核排名；業績統計僅供內部參考（v1 的歸屬資料為自報，見 A-19）。
- **不做**機器學習或統計預測模型；補貨建議採可手算的公式（見 A-16），確保課堂可講解、驗收可重算。
- **不做**多倉、多店、跨店庫存調撥。
- **不做**自助註冊（帳號由管理員建立）、密碼重設信、SSO／OAuth、多因素驗證、忘記密碼流程。
- **不做**多租戶／多公司、跨機器的中央帳號目錄。
- **不做**條碼／QR Code 掃描、POS 機串接、電子秤串接、EDI 對接。
- **不做**行動裝置原生 App（v1 僅網頁介面，行動裝置以瀏覽器使用）。
- **不做**即時推播（Line Notify、Email 通知）；補貨警示與低庫存警示以查詢方式提供。
- **不做**雲端部署、多人協同一份資料庫、遠端備份服務（v1 備份以 `pg_dump` 檔案為準）。
- **不做** AI 功能（預測補貨、OCR、自然語言查詢）作為 v1 交付範圍；理由見 §8 OQ-4。`[NOTE FOR PM: 若課程要求交付物必須含 AI 應用情境，此節需要重寫；屆時建議以「把補貨建議升級為趨勢預測」或「報表自然語言問答」做為教學展示加項，並以 `bmad-deep-recon` 先做研究再定案。]`
- **不追求**成為通用 ERP 或取代既有專業軟體。

## 6. MVP 範圍

### 6.1 納入範圍

- 品項主檔：建立、查詢篩選、修改、停用（FR-1 ～ FR-3）
- 入庫：多品項入庫單、送出、查詢、沖銷更正（FR-4 ～ FR-6）
- 出庫：多品項出庫單、送出（含庫存不足阻擋與銷貨員歸屬）、查詢（FR-7 ～ FR-8）
- 庫存查詢與低庫存警示清單（FR-9 ～ FR-10）
- 盤點：建立盤點單、強制填寫差異原因、送出、差異報表（FR-11 ～ FR-13）
- 異動紀錄：明細查詢、不可竄改、CSV 匯出（FR-14 ～ FR-16）
- 報表：進銷存概況、庫存總值、CSV 匯出（FR-17 ～ FR-18）
- **補貨判斷：建議清單（公式可手算）、補貨統計報表、建議清單匯出（FR-19 ～ FR-21）**
- **銷貨員業績：銷貨員檔案、出庫歸屬、業績統計與排名、明細下鑽、CSV 匯出（FR-22 ～ FR-26）**
- 跨領域 NFR-1 ～ NFR-9 全部適用
- 一份繁體中文操作手冊（Markdown + HTML），含補貨公式與業績計算說明
- 以 `bmad-architecture` 產生的技術架構文件與 `bmad-create-epics-and-stories` 產生的 epic/story 清單（下游交付物）

### 6.2 MVP 不納入

| 項目 | 理由 | 預定 |
|------|------|------|
| 供應商／採購下單 | 擴大範圍，且 v1 痛點未證實；補貨建議只輸出清單 | v2 |
| 使用者帳號與權限 | 單機環境無必要；業績歸屬為自報（A-19） | v2 |

| 機器學習預測模型 | 教學情境要求可解釋、可手算 | v2／選做 |
| 條碼／POS 串接 | 需額外硬體與金流整合 | v2 |
| 品項批次匯入（CSV） | 資料量小時手動建立即可 | v2 |
| AI 輔助（LLM 查詢、影像辨識） | 未完成可行性與痛點研究 | 待 OQ-4 決議（可作課程加值展示） |
| 行動裝置原生 App | 網頁已可滿足 | v3 |
| 雲端部署 | 與「本機可交作業」目標衝突 | 不做 |
| 會計／成本核算 | 超出業務範圍 | 不做 |
| 補貨建議的自動下單與供應商比價 | 需供應商資料 | v2 |

## 7. 成功指標

> 每個指標標註驗證的需求編號；反指標用來防止為達標而做出有害行為。

**主要**
- **SM-1**：**主線流程可獨立完成率** — 首次接手的操作者（無工程背景）能在 15 分鐘內、不看說明文件的情況下完成「建立品項 → 入庫 → 出庫 → 查庫存」四步（若失敗則須允許看說明文件）。驗證 FR-1、FR-4、FR-7、FR-9；驗收方式：3 位試用者操作測試。
- **SM-2**：**盤點可完成率** — 盤點單能在單次工作階段內完成，差異原因填寫率 100%（系統阻擋未填者送出）。驗證 FR-11、FR-12。
- **SM-3**：**數字可追溯率** — 抽查任一品項，其「期末庫存現量」可由「期初 + 入庫 − 出庫 + 盤點差異」100% 重算相符，且每筆異動可追溯到單據。驗證 FR-14、FR-15、FR-17。
- **SM-4**：**帳實相符率** — 每月盤點結束後，盤點差異筆數占比 ≤ 5%（盤點差異筆數 ÷ 盤點品項數），且無單一品項連續三個月皆有差異。驗證 FR-13、FR-17。
- **SM-8**：**補貨判斷可解釋率** — 抽樣 10 個補貨建議，100% 可由「安全庫存 + 日均消耗 × 前置天數 − 庫存現量」在 5 分鐘內手算重現同一建議量。驗證 FR-19；這是本專案最重要的可教學性指標。
- **SM-9**：**業績數字對得上** — 業績彙總與明細加總、与出庫單資料三方一致率 100%；「未歸屬銷售」合計可被使用者指出原因。驗證 FR-23、FR-24、FR-25。

**次要**
- **SM-5**：**查詢回應時間** — 典型查詢 95 百分位 ≤ 2 秒；補貨判斷與業績統計 ≤ 3 秒。驗證 NFR-3。
- **SM-6**：**單據更正可追溯** — 所有更正皆以反向紀錄表達，100% 可由原始紀錄追溯。驗證 FR-6、FR-15。
- **SM-7**：**交付完整度** — 課程成果發表所需文件（PRD、架構、epic/story、驗收結果、操作手冊）齊備。驗證 NFR-8、NFR-9。
- **SM-10**：**補貨建議可用性** — 使用者每週實際用補貨建議清單下單的比例 ≥ 80%（主觀評估 + 教師訪談）。驗證 FR-19、FR-21。
**SM-11**：**登入可用性** — 新使用者能在 60 秒內自行登入並完成一次出庫登錄；管理員新增一個帳號的時間 ≤ 2 分鐘。驗證 FR-28、FR-29。
**SM-12**：**歸屬可信度** — 抽查 20 筆出貨，記錄者與銷貨員歸屬皆等於實際作業者的登入帳號，無代填跡象。驗證 FR-31。

**反指標（不應被優化）**
- **SM-C1**：**功能數量** — 不以「功能多」為成功標準。防止為求廣而淺（本產品價值在正確性與可追溯，不在功能數）。
- **SM-C2**：**零錯誤率追求** — 不以「不允許使用者送出任何單據」為目標；正確的阻擋加上可解釋的錯誤訊息，比零阻擋更重要。
- **SM-C3**：**自動化取代人工** — 不以「完全免除人工輸入」為目標。庫存數字的正確性優先於輸入便利性。
- **SM-C4**：**密碼便利性** — 不以「讓程式自動連線不用輸入密碼」為目標。密碼不落地優先於連線便利。
- **SM-C5**：**補貨建議的「準」** — 不以「預測越準越好」為目標。v1 追求可解釋與可維護；為提高準確度而引入黑箱模型，是本專案明確不做的取捨（見 §5）。
- **SM-C6**：**業績數字的權威性** — 不以「業績報表可作為考核依據」為目標。v1 的歸屬為自報，用途限於教學展示與內部參考。

## 8. 待確認問題

> 這些是尚未解決、會影響後續工作（架構、epic、實作）的問題。

1. **OQ-1 真實使用者與訪談**：目前的使用者描述是依課堂框架推導的「小陳商店」情境。是否要做 1–2 次真實訪談（店主或倉管）以校準痛點與流程？`[NOTE FOR PM: 課程框架強調「痛點須證據化」，若無訪談，本 PRD 的痛點段落僅為假設。]`
2. **OQ-2 競品與替代方案**：同類工具有哪些（商用軟體、試算表模板、开源專案）？目前採「全部自建」策略未做外部參考。課程《企業痛點盤點與 AI 應用情境分析》要求比較自建／外購／委外／PoC。
3. **OQ-3 資料與流程現況（As-Is）**：目前實際用什麼記帳？紙本、Excel、LINE 群組？資料從哪裡來、格式為何、每日筆數量級？這些直接影響遷移與輸入效率設計，**也影響補貨建議的計算區間是否合理**（若只有幾週的資料，30 天區間的統計意義有限）。
4. **OQ-4 AI 應用是否納入交付範圍**：課程為 AI 實戰課程，課題是否要求交付物含 AI 應用情境（例如把補貨建議升級為趨勢預測、報表自然語言問答、條碼 OCR）？目前列為 v1 非目標、可作課程加值展示項。
5. **OQ-5 供應商／採購管理是否為必要範圍**：警示清單與補貨建議的最終用途是補貨，但 v1 不做採購。是否接受「只做清單輸出、不做採購流程」？
6. **OQ-6 品項資料匯入**：若初始品項數量為數百筆，手動建立是否可接受？是否需要 CSV 匯入？
7. **OQ-7 技術棧偏好**（✅ 已於 2026-10-21 解決：React 前端 ＋ Python Flask 後端 ＋ Flask-Migrate/Alembic ＋ PostgreSQL）：原假設為 Web（本機 Express／Next.js + PostgreSQL）。使用者指定改用 React + Flask，schema 以 Flask-Migrate 管理。
8. **OQ-8 盤點基準與並行作業**：盤點進行中若仍有入庫出庫，基準如何處理？（本 PRD 假設盤點基準時間送出時鎖定，盤點期間不鎖庫存。）
9. **OQ-9 記錄者的真實身分**：v1 只存自由文字的「記錄者」。是否需要固定的人員清單（不帶密碼）？→ 已由 FR-22 銷貨員檔案部分回答，剩餘問題為「倉管／店主是否也需要一份人員清單」。
10. **OQ-10 課程交付期限與評分標準**：影響 MVP 範圍是否需要再收斂（v0.2 已把範圍擴到 26 條 FR，時間壓力須確認）。
11. **OQ-11 補貨前置天數由誰維護、是否每品項不同？**（✅ 已於 2026-10-21 解決：**每品項設定**）使用者指定採品項層級，於品項主檔維護（預設 7 天）；`products` 需新增 `lead_time_days` 欄位。
12. **OQ-12 業績的「金額」定義**：目前以「出庫數量 × 品項單價」計（售價口徑）。是否需要改用成本價？是否需要「平均售價」概念（若單價隨時間調整）？
13. **OQ-13 是否需要區分通路／店別？** 目前 v1 為單一營業地點、單一店別；若補貨與業績需跨店比較，需擴充模型。
14. **OQ-14 銷貨員歸屬的防呆機制**：v1 為自報。是否需要「每台終端機鎖定一位銷貨員」的簡易做法（設定檔指定，開啟時帶出）？這會降低代填風險但降低彈性。
15. **OQ-15 前端技術細節**（✅ 已於 2026-10-21 解決：JavaScript 而非 TypeScript；UI 套件 Ant Design；圖表 Recharts；路由 react-router-dom；資料存取用 fetch + React hooks）：使用者指定以 **JavaScript** 實作；其餘選型為預設建議，於 `bmad-architecture` 定案（A-26）。
16. **OQ-16 啟動方式**（✅ 已於 2026-10-21 決定：**開發期前後端各開一個終端機，正式啟動時單一指令**）：Flask 跑在 5000（API ＋正式環境的前端靜態檔），React 以 Vite dev server 跑在 5173 並把 `/api` proxy 到 Flask。上課展示／交付時用 `npm run build` 產出靜態檔，由 Flask 單一啟動。
17. **OQ-17 Python 套件管理**（✅ 已於 2026-10-21 決定：**用 `uv`**）：環境已有 uv 0.13.1，安裝指令更短、可鎖版本，且與 BMAD 的 Python 腳本共用同一套工具鏈。以 `uv venv` ＋ `uv add` 管理依賴，lock 檔納入版控（A-27）。
18. **OQ-18 資料庫 driver 選擇**：`psycopg`（v3）對 Python 3.14 是否有 wheel？若無則用 `psycopg2-binary`。建議在架構階段先驗證（A-24）。
19. **OQ-19 Session 有效時間**：登入後多久要重新登入？v1 暫定 8 小時或關閉瀏覽器即失效（教學情境），是否可接受？
20. **OQ-20 密碼政策與管理員自救**：只要求至少 8 碼是否夠？管理員若忘記自己密碼，目前沒有「重設」功能（只能改資料庫）——是否由「管理員可重設他人密碼」即可滿足？
21. **OQ-21 「記住我」**：是否需要記住登入狀態（長效 cookie）？v1 暫定不做，電腦重開要重登。

## 附錄 B：As-Is / To-Be 流程

**As-Is（現況，課堂情境推導）**

1. 供貨商送貨到店 → 陳姐清點數量
2. 陳姐在紙本或手機記事本記下「可樂 36 瓶」
3. 紙本放在櫃台下，隨手寫、隨手撕
4. 進貨商品上架，陳姐用記憶補貨（補多少憑感覺，缺貨了才發現）
5. 顧客買走商品 → 銷量靠記憶或事後憑發票回推
6. 月底店主盤點 → 逐項比對紙本與實物 → 發現對不上
7. 回頭找原因，但紙本沒有完整紀錄，只能憑印象調整
8. 想知道哪個品項賣得快、哪個店員賣得好 → 翻發票、問店員、憑印象
9. 交班時口頭交代剩餘數量，新人無憑據接手

**To-Be（目標）**

1. 供貨商送貨 → 陳姐開啟「入庫」，勾選品項、填數量、一次送出（FR-4）
2. 系統即時更新庫存現量並顯示「原值 → 新值」
3. 庫存現量隨時可查（FR-9），低於安全庫存自動進警示清單（FR-10）
4. 顧客購買或內部領用 → 出庫單登記（FR-7），指定銷貨員；庫存不足立即被擋下
5. 每週訂貨前 → 開啟「補貨判斷」，看建議品項與建議量（FR-19），匯出清單給跑商
6. 月底盤點 → 建立盤點單輸入實盤數 → 系統算差異 → 未填原因不可送出（FR-11、FR-12）
7. 盤點差異保留在差異報表中（FR-13），反覆差異可被看見
8. 每月初 → 開啟「銷貨員業績」看各人銷售金額／件數／品項數並可下鑽明細（FR-24、FR-25）
9. 任何時點可用「進銷存概況」回答「這個月進多少、出了多少、剩多少」（FR-17）
10. 交接只需交出這台電腦 + 操作手冊；新人照著做即可（UJ-4、NFR-5）

**流程分類（對應框架第 9 頁 BPI）**：本專案判斷為**「優化」**而非「再造」——現有流程順序合理，問題出在資料分散與無紀錄，不需重新設計作業順序。補貨與業績屬於**新增的判斷輔助**，不取代既有作業流程。

## 附錄 C：使用者故事與驗收條件

> 格式依框架第 8 頁：User Story（誰、為什麼、價值）＋ Acceptance Criteria（可測試、可量化、可驗收）。供 `bmad-create-epics-and-stories` 轉成 epic/story。

**Story-1：建立品項**
身為**倉管人員**，我希望**建立品項主檔（sku、名稱、分類、單位、單價、安全庫存）**，以便**之後的入庫與出庫可以直接選擇、不必每次重打**。
驗收條件：
- 輸入完整且 sku 未重複 → 建立成功，列表出現新品項。
- sku 重複 → 拒絕儲存並指出重複對象。
- 名稱或 sku 留空 → 拒絕儲存並標示缺漏欄位。

**Story-2：收貨入庫**
身為**倉管人員**，我希望**建立多品項入庫單並一次送出**，以便**收貨當下就讓庫存數字正確**。
驗收條件：
- 送出後，庫存現量 = 原值 + 該單所有品項數量總和。
- 數量 0 或負數 → 拒絕送出並指出是哪一列。
- 送出後畫面列出「品項：原數 → 新數」對照。

**Story-3：出貨與庫存不足阻擋**
身為**店員**，我希望**登錄出貨並在數量不足時被即時阻止**，以便**不會賣出自己不知道的數量**。
驗收條件：
- 庫存足夠 → 送出成功，庫存現量正確扣減。
- 出庫數量 > 庫存現量 → 拒絕送出並顯示「庫存不足：品項 X 現有 N，需 M」。

**Story-4：盤點差異**
身為**店主**，我希望**在盤點時輸入實盤數並為每個差異填寫原因**，以便**知道數字為什麼對不上、錯在哪**。
驗收條件：
- 輸入實盤數即時顯示帳面數與差異（正 = 盤盈、負 = 盤虧）。
- 有差異品項未填原因 → 無法送出，系統指出缺哪一列。
- 送出後產生盤點差異異動，庫存現量 = 實盤數。

**Story-5：數字可追溯**
身為**店主**，我希望**隨時查得到某個品項的每一筆數量變化**，以便**被問到數字時可以說清楚來歷**。
驗收條件：
- 查詢某品項全部異動，依序累加結果 = 目前庫存現量。
- 每筆異動顯示時間、類型、數量、當時庫存現量、單據號、記錄者。
- 嘗試修改或刪除既有異動 → 系統拒絕。

**Story-6：低庫存補貨清單**
身為**倉管人員**，我希望**看到低於安全庫存的品項清單**，以便**安排補貨、決定這週要訂哪些貨**。
驗收條件：
- 清單只含「庫存現量 < 安全庫存」且啟用中的品項。
- 補足後該品項不再出現在清單中。
- 安全庫存 = 0 的品項不出現在清單中。

**Story-7：進銷存報表**
身為**店主**，我希望**看某個時間區間的進銷存概況並匯出**，以便**調整下個月的進貨量**。
驗收條件：
- 期末 = 期初 + 入庫 − 出庫 + 盤點差異（可重算相符）。
- 金額 = 數量 × 單價，顯示至小數第二位。
- 匯出 CSV 可用 Excel 開啟且中文不亂碼。

**Story-8：交接**
身為**新進人員**，我希望**照著操作手冊就能完成入庫與盤點**，以便**不需要靠口頭交接就能接手**。
驗收條件：
- 手冊涵蓋：啟動、設定記錄者、品項建立、入庫、出庫、盤點、查詢、報表、補貨判斷、業績、備份。
- 未受過訓練者在無口頭指導下，依手冊可完成一次完整盤點（SM-1 驗收）。

**Story-9：補貨建議（使用者明確需求）**
身為**店主**，我希望**看到依近期銷售速度算出的補貨建議清單（哪些品項要補、補多少）**，以便**不再憑印象訂貨、避免缺貨與滯銷**。
驗收條件：
- 畫面顯示品項、庫存現量、安全庫存、日均消耗、預計用完日、建議進貨量，並標示計算區間與前置天數。
- 建議進貨量 = max(0, 安全庫存 + 日均消耗 × 前置天數 − 庫存現量)（可用手算重現）。
- 區間內無出庫紀錄的品項不列入建議清單，改列「無消耗資料」清單。
- 切換計算區間（7／30／90 天）後，建議清單內容隨之改變。
- 建議清單可匯出 CSV，檔案內標註區間與前置天數。

**Story-10：銷貨員業績（使用者明確需求）**
身為**店主**，我希望**看到每位銷貨員在期間內的銷售金額、件數與品項數，並可查看明細**，以便**了解各人貢獻並安排排班**。
驗收條件：
- 每位銷貨員顯示銷售金額、件數、品項數，排名依金額排序（可切換以件數排名）。
- 金額 = 銷售用途出庫數量 × 單價；明細加總必須等於彙總數字。
- 用途為「銷售」但未指定銷貨員的出庫單 → 送出不符者被阻擋；未指定者不計入任何人業績，並在「未歸屬銷售」合計中列出。
- 可點選某人下鑽到每筆明細，每筆可連結回原出庫單。
- 業績可依期間、品項、銷貨員篩選並匯出 CSV。
