# 庫存管理系統 — Experience Spine

> 單機版桌面 Web 介面（React 19 + Ant Design 6），跑在本機瀏覽器。視覺識別由 `DESIGN.md` 定義；本文件定義**資訊架構、行為、狀態、互動、可及性與關鍵流程**。兩份 spine 與任何 mock 或線框圖衝突時，**以 spine 為準**。

## Foundation

- **表單因子**：桌面瀏覽器 Web（本機單機部署，Flask 同時提供 API 與靜態檔）。主要使用情境是**站在貨品旁邊、單手操作**；手機瀏覽器可讀（查庫存、看報表），但**不提供寫入操作**（入庫／出庫／盤點在手機不顯示送出按鈕）。
- **UI 系統**：Ant Design 6（React）。設計紀律是「沿用 antd 預設，只疊加 `DESIGN.md` 定義的品牌層增量」。元件視覺規格以 antd 與 `DESIGN.md.Components` 為準。
- **單一作業模式**：v1 無登入、無權限。所有動作共用一個「**記錄者**」值（設定頁維護，預設帶入每次單據），對應 PRD 的詞彙表與 AD-13。
- **語言**：繁體中文。介面用語一律沿用 PRD 詞彙表（品項／庫存現量／入庫／出庫／盤點差異／補貨建議／業績）。
- **語言界線**：此介面是給單一操作者用的內部工具，不做多人協作、不做權限、不做審核流。

## Information Architecture

| 畫面 | 進入方式 | 用途 | 階段 |
|---|---|---|---|
| 儀表板 | 開啟 App（預設路由 `/`） | 今日摘要：庫存現量總值、低庫存品項數、最近異動、本週待辦（該盤點了） | M1 |
| 品項 | 側邊選單 `/products` | 品項主檔的建立、查詢、修改、停用 | M1 |
| 入庫 | 側邊選單 `/stock-in`、庫存頁快捷動作 | 收貨登記（多品項單） | M1 |
| 出庫 | 側邊選單 `/stock-out`、庫存頁快捷動作 | 銷售／領用／報廢登記，歸屬銷貨員 | M1 |
| 庫存查詢 | 側邊選單 `/stock` | 目前庫存現量、低庫存警示清單 | M1 |
| 盤點 | 側邊選單 `/stocktake` | 建立盤點單、輸入實盤數、差異原因、送出 | M1 |
| 異動紀錄 | 側邊選單 `/movements` | 庫存異動明細查詢、匯出 CSV | M1 |
| 報表 | 側邊選單 `/reports` | 進銷存概況、庫存總值、匯出 CSV | M1→M2 |
| 補貨判斷 | 側邊選單 `/replenishment` | 補貨建議清單、補貨統計、匯出清單 | M2 |
| 銷貨員業績 | 側邊選單 `/performance` | 業績排名、業績明細、匯出 | M2 |
| 設定 | 側邊選單 `/settings` | 記錄者、預設補貨前置天數、備份說明、示範資料 | M1 |

**導覽原則**

- 固定左側導覽，依**工作流**而非資料表分組：
  - 「日常作業」：入庫、出庫、盤點
  - 「查詢」：庫存查詢、異動紀錄
  - 「分析」：報表、補貨判斷、銷貨員業績
  - 「設定」：品項、設定
- 品項（主檔）在日常作業中是最常被開啟的頁面之一，因此放在設定分組但**固定顯示在最上方**，不是最下方。
- 每個頁面標題列右側固定一個主要動作按鈕（例：品項頁的「＋ 新增品項」）。
- 儀表板**不取代**任何功能頁，它只回答「現在該做什麼」。

**深層連結規則**：`/products?keyword=可樂&category=飲料`、`/movements?product_id=12` 這類查詢條件要能寫進網址，讓使用者可以把畫面丟給別人。

## Voice and Tone

文案以繁體中文書寫，語氣是「同事之間的清楚交代」，不是行銷。品牌語氣在 `DESIGN.md.Brand & Style`。

| 情境 | 這樣寫 | 不要這樣寫 |
|---|---|---|
| 空狀態 | 「還沒有品項。先建立一個品項，才能登記入庫。」 | 「暂无数据」「快来创建吧！」 |
| 送出成功 | 「入庫成功：可樂 500ml，庫存 24 → 60」 | 「操作成功 ✓」 |
| 送出被擋 | 「無法送出：可樂 500ml 庫存不足，目前 12、需 20。先入庫或改數量。」 | 「庫存不足」 |
| 盤點差異未填原因 | 「還有 2 個品項沒填差異原因，補完才能送出。」 | 「請填寫必填欄位」 |
| 查無資料 | 「這段期間沒有出貨紀錄。」 | 空白表格 |
| 導覽提示 | 「依序：選品項 → 填數量 → 送出」 | 「歡迎使用庫存管理系統！」 |

**規則**

- 先講**發生什麼**，再講**該怎麼辦**；錯誤訊息必須帶具體數字（目前 12、需 20）。
- 不用表情符號、不用驚嘆號疊加、不用「您」敬語（單一作業系統，語氣平等）。
- 同一個數字在畫面上出現兩次時，兩次都要出現（例：提示「庫存 12」與表格裡的 12 必須一致）。
- 複合的業務名稱一律用 PRD 詞彙表，不要用使用者可能不懂的術語（「盤點差異」而不是「庫存調整項」）。

## Component Patterns

視覺規格在 `DESIGN.md.Components`（或 antd 預設）；此處只定義**行為**。

| 元件 | 用在哪 | 行為規則 |
|---|---|---|
| 單據表單（入庫／出庫） | 入庫頁、出庫頁 | 上方單據資訊（單號、日期、記錄者、用途、備註）＋下方明細表。明細表可「新增一列」，每列一個品項下拉＋數量＋單價。送出前顯示即時合計：總數量、總金額。已送出單據以唯讀模式檢視，**不提供編輯**（改用沖銷）。 |
| 盤點表單 | 盤點頁 | 逐品項輸入實盤數；輸入後即時顯示帳面數、差異（正＝盤盈、負＝盤虧）與差異原因下拉（損壞／報廢／被取用未登記／搬運損失／其他，需附自由文字）。**有差異但未填原因時，該列標示橘色警示**。 |
| 差異彙整列 | 盤點頁頂部 | 固定顯示「本單共 N 個品項、差異 M 個、已填原因 K 個」。M > K 時送出行為阻擋並捲動到第一個缺原因的列。 |
| 低庫存警示條 | 庫存頁、儀表板 | 只有在有低庫存品項時出現（`{colors.low-stock-alert}`）。內容列出品項與缺口，不做逐項點擊。 |
| 庫存現量欄 | 所有表格 | 右對齊、等寬數字（`{typography.numeric.fontVariantNumeric}`）。若為負數，以 `error` 色顯示並附「負庫存」標籤。 |
| 業績排名表 | 業績頁 | 依銷售金額排序，可切換以件數排序。**每列右側固定標註「自報資料」**（見 Foundation 的 A-19 假設）。點擊列 → 下鑽明細頁。 |
| 補貨建議表 | 補貨頁 | 每列顯示品項、庫存現量、安全庫存、日均消耗、預計用完日、建議進貨量。**表頭固定顯示計算區間與前置天數**（避免使用者誤認數字）。建議量為 0 的品項不列出。 |
| 未歸屬銷售提示 | 業績頁 | 若期間內有未指定銷貨員的銷售，頁面頂端顯示警示條與金額，讓店主知道有資料漏歸屬。 |
| 匯出按鈕 | 所有清單頁與報表頁 | 統一在頁面右上或表格上方工具列，標籤為「匯出 CSV」。匯出後以 `message` 告知筆數。 |
| 確認對話框 | 送出單據、沖銷、停用品項 | 送出單據用 `Popconfirm` 簡短確認；**沖銷與停用**（不可逆的稽核行為）用 `Modal`，需輸入原因或確認文字。 |
| 數字欄位 | 所有輸入 | 數量用 `InputNumber`，不得輸入小數、不得為負；單價與金額保留兩位小數。 |

## State Patterns

| 狀態 | 畫面 | 處理方式 |
|---|---|---|
| 冷啟動載入 | 所有頁面 | antd `Skeleton`，列數貼近實際列數；不顯示全屏遮罩（避免使用者以為當掉）。 |
| 首次使用（無品項） | 儀表板、品項頁 | Empty state：「還沒有品項。先建立一個品項，才能登記入庫。」＋「＋ 新增品項」按鈕。 |
| 查無結果 | 清單頁 | Empty state 帶上**已套用的條件**：「沒有符合『飲料』且庫存低於 10 的品項。」＋「清除條件」動作。 |
| 資料筆數為零的區間 | 報表頁 | 顯示區間與「此區間無資料」，不是空白。 |
| 送出被擋 | 單據表單 | **不清空表單**；錯誤以 `Alert`（`error`）顯示在該列下方，含具體數字；焦點移到第一個問題列。 |
| 盤點有差異未填原因 | 盤點表單 | 橘色警示條 ＋ 該列橘色標示 ＋ 送出行阻擋 ＋ 捲動定位。 |
| 送出成功 | 單據表單 | `message` 顯示「入庫成功：可樂 500ml，庫存 24 → 60」；表單清空並留在原頁（不跳轉），方便連續登錄下一張單。 |
| 提交中 | 所有送出動作 | 按鈕進入 `loading` 並停用，避免重複送出（後端交易內部也會擋）。 |
| 提交失敗（伺服器錯誤） | 所有頁面 | 保留使用者已輸入的內容，`Alert` 顯示錯誤訊息，並提供「重試」。 |
| 低庫存 | 庫存頁、儀表板 | 警示條 ＋ 表格內以 `accent` 色標籤標示，不整頁變色。 |
| 業績資料為自報 | 業績頁 | 固定標註「資料為使用者自填，非稽核結果」，並在匯出檔案的說明列帶上同樣字樣。 |
| 補貨建議資料不足 | 補貨頁 | 區間內無出庫紀錄的品項另列「無消耗資料（可能滯銷）」清單，不列入建議。 |

## Interaction Primitives

**滑鼠優先、鍵盤可完成**。這個工具的使用者常常一手拿貨、一手操作，不假設雙手都空著，但所有流程都必須能只用鍵盤走完。

- **Enter** —— 表單內送出；在明細表的最後一列按 Enter 新增下一列（連續登錄時的關鍵路徑）。
- **Esc** —— 關閉最上層 Modal／Popconfirm；取消表單中的「新增一列」。
- **Tab** —— 順序等同閱讀順序；明細表的品項 → 數量 → 單價依序。
- **`/`** —— 在清單頁聚焦搜尋框。
- **滑鼠** —— 點擊列開啟明細；hover 顯示列內快捷動作（檢視、沖銷）；拖曳排序 v1 不做。
- **數字欄位** —— 上下方向鍵微調數量（步進 1），輸入時允許直接鍵入數字。

**全面禁止**：無限捲動（只用分頁）、hover 隱藏的必要操作（手機）、多層 Modal 堆疊、任何一鍵批次刪除已送出的單據。

## Accessibility Floor

視覺對比在 `DESIGN.md`（繼承 antd 預設，維持 WCAG AA 對比）。

- 目標 **WCAG 2.2 AA**。所有文字與背景對比 ≥ 4.5:1，大字 ≥ 3:1。
- 螢幕閱讀器在換頁時朗報畫面名稱與筆數，例：「庫存查詢，24 筆資料」。
- 導覽使用 landmark 語義（`nav` / `main`），跳至主要內容的連結必須存在。
- 所有錯誤提示以 `aria-live="assertive"` 宣告，焦點移到第一個問題欄位。
- 焦點外框必須可見（沿用 antd focus token），不得移除。
- 表格使用真實的 `table`、`th`（含 `scope`），排序與篩選狀態以 `aria-sort` 標示。
- 顏色不是唯一訊息通道：低庫存除了橘色也一定有文字標籤；盤點差異正負號同時用文字「盤盈／盤虧」。
- 觸控目標最小 44×44px（antd 預設 32px 在主要動作按鈕上调高）。
- 支援瀏覽器縮放至 200% 不破版。

## Responsive & Platform

| 斷點 | 行為 |
|---|---|
| `≥ 1280px` | 左側導覽固定顯示（200px）；表格滿寬；表單限寬 960px。 |
| `1024–1279px` | 同上，內容區縮窄。 |
| `768–1023px` | 左側導覕收成圖示；單據明細表改為「卡片式列」呈現（每個品項一張卡），避免橫向捲動。 |
| `< 768px` | 導覽為抽屜；**唯讀模式**——查詢、庫存、報表、業績、補貨可看；入庫／出庫／盤點的「送出」按鈕不顯示，頁面頂端顯示「請在電腦上完成登錄」。 |

**平台**：桌面優先的響應式網頁，不是原生行動 App。行動裝置定位為「走到貨旁邊時查一下」。

## Inspiration & Anti-patterns

- **借用自 Ant Design**：整個介面詞彙。這個產品的視覺語言是「antd 預設 + 品牌層增量」，這是刻意的取捨，不是偷懶。
- **借用自零售 POS / 倉管軟體**：單據明細「一列一項、快速連續輸入」的表格體感；數量欄永遠在最右、Enter 續行下一列。
- **借用自財務軟體**：數字欄一律等寬右對齊、小數點垂直對齊、金額固定兩位小數、期初／入庫／出庫／期末的橫向對照列。
- **拒絕 — 深色模式為預設**：v1 只用亮色，專注在數字可讀性；深色模式列為 v2。
- **拒絕 — 動畫與微互動**：不做頁面轉場動畫、不做數字滾動動畫、不做慶祝動畫。倉庫現場的機器常常又慢又舊，動畫只會礙事。
- **拒絕 — 儀表板圖表裝飾**：儀表板只放數字與清單，不放環形圖。判斷靠表格，不靠視覺。
- **拒絕 — 對話框式表單 wizard**：入庫不分成「第一步、第二步」的多步驟精靈。單據不複雜，流程越短越好。

## Key Flows

> 主角名稱沿用 PRD §2.3 的具名角色，情境取自 PRD 的使用者旅程。

### Flow 1 — 收貨入庫（陳姐，早上 9:05，店門口貨車剛卸完）

1. 陳姐開著筆電坐在收銀台後方，打開「入庫」頁。
2. 頁面載入記錄者「陳姐」與今天的日期；她按下「＋ 新增一列」。
3. 品項下拉輸入「可」→ 篩出「可樂 500ml」→ 選取（畫面同時顯示目前庫存 24，讓她知道這批進來會變成多少）。
4. 數量欄輸入 36，Enter 後自動新增下一列並聚焦在品項欄。
5. 第二列輸入「洋芋片 70g × 12」，備註欄打「供應商 A 到貨」。
6. 頁面底部即時顯示「共 2 個品項、48 件、合計 1,150.00」。
7. 按「送出入庫單」→ Popconfirm 確認 → 送出。
8. 成功訊息：「入庫成功：可樂 500ml，庫存 24 → 60；洋芋片 70g，庫存 40 → 52。」表單清空，停留在原頁可繼續登錄下一張。
9. 陳姐回到櫃檯。當天下午有人問「還有多少可樂」，她到「庫存查詢」輸入「可樂」，右對齊的 60 就在那裡。

### Flow 2 — 月底盤點（阿豪，月底營業結束後，店裡已清點完畢）

1. 阿豪打開「盤點」→ 新增盤點單（日期預設今天）。
2. 他輸入實盤數：可樂 57（帳面 60）。該列即時顯示「盤虧 3」，並出現橘色的「差異原因」必填欄。
3. 他從下拉選「損壞／報廢」；若需補充說明則填自由文字。
4. 頁面頂部差異彙整列更新：「共 12 個品項、差異 2 個、已填原因 1 個」。
5. 他忘了其中一列的原因，直接按「送出盤點單」→ **送出被擋**，橘色警示條：「還有 1 個品項沒填差異原因，補完才能送出。」畫面捲到那一列。
6. 補完原因後送出。成功訊息：「盤點完成：2 個品項差異已記錄（盤盈 1、盤虧 1）。」
7. 他到「盤點差異報表」看到本月所有差異，點進某品項可看到這張盤點單的帳面數、實盤數、原因與時間。

### Flow 3 — 補貨判斷（陳姐，週一早上開店前，決定這週訂哪些貨）

1. 陳姐打開「補貨判斷」，畫面頂端顯示「計算區間：最近 30 天 　補貨前置天數：依各品項設定 　計算時間：2026-10-21 08:50」。
2. 建議清單列出 3 個品項：優酪乳 500ml（現有 12、日均消耗 4.3、建議補 30）、泡麵 碗裝（現有 40、日均消耗 6.0、建議補 12）、衛生紙（現有 6、日均消耗 1.1、建議補 8）。
3. 下方另有「無消耗資料（可能滯銷）」清單：3 個品項。
4. 陳姐按「匯出 CSV」交給跑商。檔案內含「計算區間」與「前置天數」兩列標註。
5. 貨到後她在「入庫」登錄，優酪乳的建議量隨消耗速度自動變化。

### Flow 4 — 看銷貨員業績（阿豪，月初，想了解三個店員的表現）

1. 阿豪打開「銷貨員業績」，期間預設「本月」。
2. 頁面頂端有一條警示條：「本月有 2 筆銷售未指定銷貨員，合計 380.00」——他先記下待會問店員。
3. 排名表列出三人：銷售金額、件數、品項數。第一名 42,800.00（件數 310）。
4. 他點擊第二名「小美」→ 下鑽明細頁：每筆出貨的日期、單號、品項、數量、單價、金額。
5. 明細加總等於彙總數字，他確認無誤後按「匯出 CSV」。
6. 頁面底部標註「資料為使用者自填，非稽核結果」。

### Flow 5 — 新人接手（實習生小美，第一次用這套系統）

1. 店主交給她操作手冊與已啟動的電腦。畫面左側導覽把「日常作業」三項（入庫、出庫、盤點）排在最上方。
2. 小美依手冊先做盤點：開啟「盤點」，看到每個品項的帳面數已填好（盤點前先產生的庫存），她只需在「實盤數」欄輸入實際數量。
3. 差異欄跳出時，手冊對應頁面告訴她「差異一定要填原因，選不到就選『其他』並寫一句話」。
4. 送出成功，她看到「盤點完成：0 個品項差異」——第一次盤點沒有差異。
5. 她再到「入庫」建立一張單，畫面底部即時顯示合計；送出後看到庫存數字變化。
6. 全程未向任何人求助，也未修改任何設定。

## Open Questions

1. **Q1** 儀表板「本週待辦（該盤點了）」——是否要記錄上次盤點日期？資料模型尚未涵蓋盤點排程（`documents` 有 `doc_date`，但無法推斷「上次盤點」）。**影響**：儀表板可少一區塊，或需加 `stocktake_schedules`。
2. **Q2** 補貨建議的「預計用完日」——以「庫存現量 ÷ 日均消耗」推算，日均消耗為 0 時不顯示。**影響**：需確認此欄位是否真的對使用者有用（老闆可能只看「建議補多少」）。
3. **Q3** 深色模式是否列為 v2？（目前拒絕，見 Anti-patterns。）
4. **Q4** 銷貨員業績頁的「排名」是否預設顯示，還是只顯示清單？排名可能帶來不必要的人際摩擦。**影響**：視覺層面的預設值。
